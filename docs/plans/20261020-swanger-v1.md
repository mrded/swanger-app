# Swanger v1: a native macOS viewer for OpenAPI schemas

## Goal

Swanger opens an OpenAPI 3.0 or 3.1 file (JSON or YAML) and shows the **resources it defines**: every request
and response body schema as an interactive block diagram, the shared fragments they're built from and where
each is used, and a **Try it** editor that checks a JSON payload against a schema with readable errors.

It is not an API explorer: no endpoint list, parameters, servers, auth or sending requests. Paths are read
only to find which schemas are request and response bodies.

Open source (MIT) from day one.

## Decisions

- **Name:** Swanger. Repo folder `~/Projects/swanger-app`. Subtitle everywhere: "OpenAPI schema viewer for
  macOS" (searches for "swanger" are corrected to "swagger").
- **Native SwiftUI throughout.** No WebKit.
- **Minimum macOS 15 Sequoia.** Swift 6 language mode.
- **Dependencies (both MIT):** [Yams](https://github.com/jpsim/Yams) for YAML;
  [ajevans99/swift-json-schema](https://github.com/ajevans99/swift-json-schema) (`JSONSchema` product only) for
  validation (99% passing Draft 2020-12 on Bowtie) and its `OrderedJSON` as the raw JSON tree, so fields keep
  the order the spec gives them.
- **Input:** OpenAPI 3.0.x and 3.1.x, JSON and YAML, `$ref`s within the file and to relative files. Swagger 2.0
  is refused with a clear message.
- **Roots and fragments:** every request body schema is a _request schema_, every response body schema a
  _response schema_; every `components/schemas` entry they reach is a _shared fragment_. Unused components
  aren't shown.
- **Distribution:** notarised Developer ID builds on GitHub Releases plus a Homebrew cask. Not sandboxed, so
  referenced sibling files are read directly.
- **Out of scope for v1:** spreadsheet export, endpoint views, Try it's form view, made-up example values,
  checking a single card on its own, multiple versions per window.
- **The model is a picture of the schema, not a validator.** Try it's validator decides what's valid; the
  diagram shows what the spec says. See [Model boundaries](#model-boundaries).

## Model boundaries

The model (`SchemaBuilder` → `SchemaNode`) exists to draw the diagram and word the rules. It is deliberately
**not** a second JSON Schema implementation. Whether a payload is valid is decided by swift-json-schema in
Try it, never by the model. This keeps the builder reviewable and stops each review from turning up another
rare combination of keywords.

**The model must:**

- never be **stricter** than the validator: anything the validator accepts, the diagram must allow.
  `ValidatorAgreementTests` enforces this, and it's the only correctness bar for keyword combinations.
- get the common OpenAPI shapes right: objects, arrays, scalars, `$ref` with siblings, `allOf` composition
  (including a closed `additionalProperties: false` member hiding other members' fields), `oneOf`/`anyOf`
  with discriminators, `if`/`then`/`else`, nullable types, recursion and fragment provenance.
- keep everything a keyword says: show it in the shape, word it as a rule or, when it can't be worded,
  fall back to a generic phrase ("the `if` schema matches", "mustn't match `not`").

**The model doesn't, by design:**

- prove a schema is unsatisfiable. Contradictions are shown as written: `{type: string, oneOf: [{type: integer}, {type: boolean}]}` is "one of integer or boolean", `enum` values the `type` rules out stay
  listed, a field that's both required and forbidden is shown as both. Only directly empty results are
  `nothing`: `false`, `not: {}`, and `allOf` members whose `type`s or `enum`s don't overlap.
- narrow a choice's variants by the outer `type`.
- work out which fields `unevaluatedProperties` sees. It's a rule only ("allows no unevaluated fields"),
  and the object stays open in the diagram.
- subtract types with `not: {type: …}`. That's a rule ("mustn't be null"), not a narrower `type`.
- merge `items` into the `prefixItems` positions of other `allOf` members. Each tuple position shows its
  own `prefixItems`.
- word conditions beyond the flat shape. An `if` is worded only when it checks fields' `const`, `enum`,
  `type` or presence, and a `then`/`else` only when it requires, forbids or limits fields directly.
  Anything else (`$ref`, `allOf`, nested fields, choices, dependencies) falls back to the condition's
  description, "the `if` schema matches" or "the `then` schema applies".
- apply `patternProperties` or an `additionalProperties` schema to named fields. Only
  `additionalProperties: false` in an `allOf` member forbids the other members' fields.
- check that `null` gets past every `oneOf`/`anyOf`. A nullable type is shown as "or null" even when a
  choice beside it rules null out.
- model `propertyNames`, `dependentSchemas`, `unevaluatedItems` or `$dynamicRef` (see the backlog).

A schema the model shows less strictly than the validator is **not a bug**, as long as no keyword is
silently dropped. A review finding about one of the cases above isn't a finding. Changing a boundary means
editing this section first, backed by real specs that need it.

## Layout

```
Package.swift                  SwiftPM: SwangerCore, SwangerValidation + tests
Sources/SwangerCore/           loading, $ref resolution, 3.0 → 2020-12, model, rule wording
Sources/SwangerValidation/     compiling schemas, validating, readable errors
Tests/SwangerCoreTests/        Fixtures/ (hand-written specs), Snapshots/
Tests/SwangerValidationTests/
App/Swanger.xcodeproj          macOS app target, depends on the local package
App/Swanger/                   SwiftUI views, document type, Info.plist, assets
.github/workflows/             ci.yml (PRs and main), release.yml (tags)
```

### 3. Loading a spec (`SwangerCore`)

- [x] `SpecLoader`: read a file URL; JSON vs YAML by extension, falling back to sniffing; YAML via Yams'
      `Node` API → `OrderedJSON`, keeping line/column for errors
- [x] Version check from `openapi`: accept `3.0.x` and `3.1.x`; `swagger: 2.0` or anything else →
      `LoadError.unsupportedVersion(found:)`
- [x] `LoadError` with file, line, column and message for parse errors
- [x] Tests: JSON and YAML fixtures load to equal trees, key order preserved, bad YAML reports its line,
      Swagger 2.0 refused

### 4. `$ref` resolution

- [x] `RefResolver`: JSON Pointer within a document (with `~0` / `~1` unescaping); relative file refs
      resolved against the referring file, each file loaded once and cached by URL
- [x] Each resolved node remembers its origin (component name or `file#pointer`), used for fragment names
- [x] Recursion: the second visit to a schema on the same path becomes a `recursive(origin)` node
- [x] Broken refs never throw: they become `unresolved(ref, reason)` nodes and are collected as warnings
- [x] Tests: local refs, cross-file refs, refs inside referenced files, a recursive tree schema, missing file,
      bad pointer

### 5. Normalising 3.0 to 2020-12

- [x] `nullable: true` → `type: [T, "null"]` (and with `enum`, add `null`); boolean
      `exclusiveMinimum`/`exclusiveMaximum` → numeric; `example` → `examples: [example]`
- [x] Runs once at load for 3.0 documents only
- [x] Tests: each conversion, and a 3.0 and a 3.1 fixture describing the same schema produce equal models

### 6. The model

- [x] Find roots: walk `paths.*.*.requestBody.content.*.schema` and `responses.*.content.*.schema`;
      prefer `application/json`, else the first JSON-like media type
- [x] Root naming: the component name when the body is a `$ref`; otherwise `<operationId> request` /
      `<operationId> <status> response`, falling back to `<METHOD> <path>`. A component used by several
      operations is one root
- [x] Root examples: the schema's `examples`, then the media type's `example` / `examples`
- [x] `SchemaNode`: object (ordered fields), array (items), scalar, choice (`oneOf`/`anyOf` variants with
      discriminator: a property that is a `const` or single-value `enum` in every variant), recursive,
      unresolved. Field: name, required, type, constraints, allowed values, format/pattern, description,
      examples, fragment used, fragment defined in
- [x] Keywords beside a `$ref` (allowed in 2020-12) tighten the fragment in place: fields forbidden with
      `not: {}`, newly required fields, extra constraints
- [x] `Rule` wording in plain English: constraints ("must be one of …", "needs at least 1 item", "allows at
      most 70 characters"); `if`/`then`/`else` as "When `status` is "Rejected": `reason` is required";
      `oneOf`/`anyOf` as one case per variant ("When `type` is "Card": …") or, without a discriminator, as
      "exactly one of / at least one of" the variants' distinguishing fields; `dependentRequired`
- [x] `FragmentIndex`: for each fragment, every root and path where it appears, direct or nested (`via`)
- [x] Root stats: field, fragment and rule counts (as on the overview cards)
- [x] `Spec` (the whole model) + `warnings: [LoadWarning]`
- [x] Tests: hand-written fixture of a small API (orders/customers/addresses, with a discriminated `oneOf`,
      an `if`/`then`, a nested fragment, a recursive schema); snapshot tests of the rule text and the
      fragment index

### 7. Validation (`SwangerValidation`)

- [x] Compile a root or fragment with swift-json-schema: wrap it in a document whose `$ref`s resolve to the
      (normalised) spec, so components and sibling files are found; cache compiled validators per schema
- [x] Turn the library's basic output into `[ValidationIssue]` (type, pointer, message), as follows:
      keyword → type (*Missing*, *Wrong type*, *Not allowed value*, *Wrong format*, *Out of range*,
      *Unexpected field*, *Rule not met*); `required`/`additionalProperties` pointers include the field;
      condition branches use the schema's `description`; drop composition summaries explained below them;
      wrong type reported once; de-duplicate
- [x] Skeleton payload for schemas with no examples: required fields only, first allowed value or a typed
      placeholder
- [x] Example naming, so the menu says "type: Card" or "with reason" rather than "Example 2": differing
      fixed values, then which optional fields are present, then one level down, then the shortest
      differing value
- [x] Test-case generator: from each example, a copy with each field in turn removed, set to `""`, `7`,
      `"zzz"`, `null`, `{}` and `[]`, and each object given an unexpected extra field
- [x] Tests: every fixture example is valid as written; each broken case gives the expected type and pointer
- [x] Known library bug (swift-json-schema 0.14): `additionalProperties` and `items` see the `properties`
      and `prefixItems` of a `$ref` beside them, so `{$ref: X, additionalProperties: false}` accepts fields
      it should reject (ajv 8 agrees they're invalid). Not fixed or reported upstream as of 0.14.2; worked
      around by compiling `{$ref: X, ...}` as `{allOf: [{$ref: X}], ...}`, which 2020-12 treats the same
      (`unevaluatedProperties` included). `ValidatorAgreementTests` now runs against `PayloadValidator`
      and no longer skips these cases

How it works, for later tasks:

- `Spec.resolvedSchemas` keeps every schema the roots and fragments reach, links in keywords the model
  doesn't show (`propertyNames`, …) included. `PayloadValidator` writes the closure of one schema into
  `$defs` of a single document, with `$ref`s rewritten to point there; an unresolved `$ref` is dropped, so
  it allows anything, as the diagram shows it unresolved.
- `format` is asserted for the library's built-in formats (`date-time`, `date`, `time`, `email`,
  `hostname`, `ipv4`, `ipv6`, `uuid`, `uri`, `uri-reference`); others are ignored.
- Messages are worded from the failing keyword's value, reusing the model's `Wording`, not taken from the
  library. A failed `oneOf`/`anyOf` reports the variant the payload was most likely meant to be: the one
  whose fixed values and type it has, else the one with fewest issues. When none fits, it reports what the
  discriminator or type would need to be, and "Needs `email` or `phone`" when the variants only miss fields.
- An array item past the last allowed one (`items: false`) is an *Unexpected field*.
- Skeletons add one item to an array whose items are objects or choices, so their fields are there to
  fill in.

### 9. App: overview, diagram, inspector

- [x] Overview: a card per request schema with stats; the fragment usage grid (rows: fragments; columns:
      schemas; filled = direct, outlined = nested; hover shows paths; "Include responses" toggle)
- [x] Diagram: cards are SwiftUI views; a custom `Layout` places them left to right; `Canvas` draws the
      connectors. Clicking a row that holds an object, array or choice opens its card; choice cards show
      one branch per variant with the discriminator; rules sit at the bottom of their card
- [x] Pan by dragging, pinch and ⌘-scroll to zoom, zoom-to-fit; double-click opens a fragment's own page or
      shows a card on its own with "Show the whole schema"
- [x] Colours: teal for top-level/required, amber for rules and decisions, violet for
      shared fragments; light and dark appearance
- [x] Inspector: the selected field's details, its rules, "defined in" and "used in" links
- [x] Search (⌘F): fields, roots and fragments, ranked by match quality. A field matches on its own name,
      never on the fields it sits inside; a dotted query (`address.postcode`) matches the end of a path; choosing a result opens and highlights it
- [x] History: every move is a history entry; ⌘[ / ⌘] and swipe go back and forward, restoring the view

How it works, for later tasks:

- `SpecStore.history` is the window's back/forward list of `ViewState`s: the page, the open rows,
  the card shown on its own, the selected row and the viewport. Opening or closing a card, showing a
  card on its own, changing page and choosing a search result are moves; selecting a row that opens
  nothing only changes the current entry, so going back isn't a click-by-click replay.
- `DiagramCards` turns a schema and its open rows into cards, parents first; `DiagramLayout` places
  them; rows all share one height (`DiagramMetrics`) so connectors can find them. A row holding an
  array of objects opens the item's card directly (`lines[]`); an array card is only shown for
  `prefixItems`.
- Paths: `FieldPath` gained `.prefixItem(Int)`, and `SchemaNode.node(at:)`/`field(at:)` follow a
  path back to its node. `SearchIndex` (in `SwangerCore`, tested) ranks exact, prefix, word start,
  then contains.
- AppKit throws "more Update Constraints in Window passes than there are views" on macOS 27 when
  the window's minimum width is less than the split view's columns need. So the window sets no
  `minWidth` of its own (the sidebar, detail and inspector minimums decide it), and the diagram
  draws its cards in an overlay so their size never becomes its minimum. The inspector still
  starts hidden, by choice.
- Swipe is the three-finger (`NSEvent.swipe`) gesture; two-finger page swipes aren't caught.

### 10. App: Try it

- [x] `Diagram | Try it` segmented control in the toolbar
- [x] JSON editor: `NSTextView` wrapper, monospaced, two-space indent on Tab, bracket matching
- [x] Examples menu (named by task 7's rules) and skeleton fallback
- [x] Debounced validation as you type; JSON syntax errors shown with their line
- [x] Issue list under the editor; clicking an issue selects its range in the text (pointer → range map) and
      its row in the diagram, climbing to the nearest field the schema has; "Valid" state
- [x] Edits kept per spec file and schema across launches

How it works, for later tasks:

- `SpecStore.mode` (`DetailMode`) switches a schema page between the diagram and Try it. It isn't
  in the history and stays as it is from page to page; leaving the diagram saves its viewport into
  the current entry. ⌥⌘D and ⌥⌘T switch too.
- `TryItModel` checks the text 300 ms after typing stops, off the main actor, and saves it as the
  draft then. Drafts are one `UserDefaults` dictionary (`tryItDrafts`) keyed by the spec's path, the
  direction and the schema's file and pointer. A page starts from its draft, else its first example,
  else its skeleton ("Required Fields Only" in the menu).
- `JSONSourceMap` (`SwangerValidation`, tested) maps pointers to UTF-16 ranges: a member selects its
  key and value; a missing one climbs to the nearest key or opening bracket. It also converts the
  parser's line and byte column to an offset, and matches brackets outside strings.
- `SchemaNode.path(to:in:)` (`SwangerCore`) turns an issue's pointer into the nearest diagram row,
  going through the variant whose discriminator value the payload has. Choosing an issue selects
  that row without a history entry (`SpecStore.revealOnThisPage`).
- Examples are printed by `JSONValue.prettyText` (`"key": value`, two spaces), not the library's
  pretty-printer, which writes `"key" : value`.
- The editor has its own `UndoManager`: with the window's, typing marked the read-only document as
  edited, and macOS restored that "Edited" mark on the next launch.

### 11. Hardening and release

- [x] Real-world specs load without warnings or crashes and in reasonable time: Petstore 3.0 and 3.1, and a
      large public spec (e.g. GitHub's or Stripe's), as a test (downloaded in CI or kept as fixtures if the
      licence allows)
- [x] UI smoke tests: open a fixture, select a schema, a valid payload shows "Valid", a broken one lists an
      issue
- [x] App icon, About window, README screenshots
- [ ] A first release through `release.yml` (task 2): ad hoc signed on GitHub Releases for now; signed,
      notarised and installed from the cask once there is a Developer ID
- [ ] Tag `v0.1.0`

How it works, for later tasks:

- `RealWorldSpecTests` loads the Petstores (fixtures, Apache 2.0) and GitHub's REST API spec
  (downloaded by `scripts/fetch-real-world-specs.sh` at a pinned commit and checksum; `make
  real-world`), then checks a skeleton against every root. GitHub's takes about 8 s unoptimised.
  Petstore 3.1 still has two warnings, for `$ref`s to an `$id` and an `$anchor`
  (`docs/backlog/refs-to-id-and-anchor.md`). Stripe's spec is left out because the model doesn't
  finish building it (`docs/backlog/large-recursive-groups-hang-the-model.md`).
- Loading and Try it's checks run on `LargeStack` (`SwangerCore`): a thread with a 64 MB stack.
  GitHub's schemas nest deep enough to overflow the 512 KB stack of a `Task.detached` thread in
  debug builds.
- The UI smoke test opens its fixture by passing the path with `-NSTreatUnknownArgumentsAsOpen YES`,
  and chooses the first example from the menu, since its own earlier run leaves a draft. It doesn't
  mask `tryItDrafts` with a launch argument: the app would then save over the real drafts. The app
  has no test-only hooks.
- The About window is a SwiftUI `Window` scene replacing the standard About item.

## Testing

- `swift test` covers the core and validation (Swift Testing), with fixtures and snapshots
- `ValidatorAgreementTests` checks that the model is never stricter than the validator (see
  [Model boundaries](#model-boundaries)). It doesn't check that the model is as strict, by design
- `xcodebuild test` runs the UI smoke tests
- CI (task 2) runs both on every pull request and on `main`, and attaches a downloadable build to each run
