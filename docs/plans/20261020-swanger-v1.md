# Swanger v1: a native macOS viewer for OpenAPI schemas

## Goal

Swanger opens an OpenAPI 3.0 or 3.1 file (JSON or YAML) and shows the **resources it defines**: every request
and response body schema as an interactive block diagram, the shared fragments they're built from and where
each is used, and a **Try it** editor that checks a JSON payload against a schema with readable errors.

It is not an API explorer: no endpoint list, parameters, servers, auth or sending requests. Paths are read
only to find which schemas are request and response bodies.

Open source (MIT) from day one.

## Decisions

- **Name:** Swanger. Repo folder `~/Projects/swanger-app`. Subtitle everywhere: "OpenAPI schema viewer for
  macOS" (searches for "swanger" are corrected to "swagger").
- **Native SwiftUI throughout.** No WebKit.
- **Minimum macOS 15 Sequoia.** Swift 6 language mode.
- **Dependencies (both MIT):** [Yams](https://github.com/jpsim/Yams) for YAML;
  [ajevans99/swift-json-schema](https://github.com/ajevans99/swift-json-schema) (`JSONSchema` product only) for
  validation (99% passing Draft 2020-12 on Bowtie) and its `OrderedJSON` as the raw JSON tree, so fields keep
  the order the spec gives them.
- **Input:** OpenAPI 3.0.x and 3.1.x, JSON and YAML, `$ref`s within the file and to relative files. Swagger 2.0
  is refused with a clear message.
- **Roots and fragments:** every request body schema is a *request schema*, every response body schema a
  *response schema*; every `components/schemas` entry they reach is a *shared fragment*. Unused components
  aren't shown.
- **Distribution:** notarised Developer ID builds on GitHub Releases plus a Homebrew cask. Not sandboxed, so
  referenced sibling files are read directly.
- **Out of scope for v1:** spreadsheet export, endpoint views, Try it's form view, made-up example values,
  checking a single card on its own, multiple versions per window.

## Layout

```
Package.swift                  SwiftPM: SwangerCore, SwangerValidation + tests
Sources/SwangerCore/           loading, $ref resolution, 3.0 → 2020-12, model, rule wording
Sources/SwangerValidation/     compiling schemas, validating, readable errors
Tests/SwangerCoreTests/        Fixtures/ (hand-written specs), Snapshots/
Tests/SwangerValidationTests/
App/Swanger.xcodeproj          macOS app target, depends on the local package
App/Swanger/                   SwiftUI views, document type, Info.plist, assets
.github/workflows/             ci.yml (PRs and main), release.yml (tags)
```

## Tasks

### 1. Repository and skeleton

- [x] `git init`; MIT `LICENSE`, `README.md` (what it is, not an API explorer, screenshots later),
      `CONTRIBUTING.md`, `.gitignore` (Xcode, `.build`, `.swiftpm`), `.swift-format`
- [x] `Package.swift`: platforms `.macOS(.v15)`, Swift 6 mode; targets `SwangerCore` (Yams, JSONSchema),
      `SwangerValidation` (SwangerCore, JSONSchema), and test targets using Swift Testing
- [x] Xcode app project `App/Swanger.xcodeproj` with the local package; bundle ID placeholder
      `io.github.<owner>.swanger`; Hardened Runtime on, App Sandbox off
- [x] Check: `swift test` passes (empty) and the app builds and launches with an empty window

### 2. CI and builds (GitHub Actions)

`ci.yml`, on every pull request and every push to `main`:

- [x] Shared settings: `permissions: contents: read`; `concurrency` per branch with `cancel-in-progress`, so a
      new push to a PR cancels the old run; a pinned macOS runner image and Xcode version (selected with
      `xcode-select`), matching what we build with locally
- [x] Job `test`: `swift-format lint --strict --recursive Sources Tests`, then `swift test --parallel`;
      cache `.build` and SwiftPM checkouts keyed on `Package.resolved`
- [x] Job `build`: `xcodebuild build-for-testing` / `test-without-building` for the app scheme (UI smoke
      tests from task 11 once they exist), then a Release build signed ad hoc (`CODE_SIGN_IDENTITY=-`);
      zip `Swanger.app` and upload it as a workflow artifact `Swanger-<short sha>.zip` (kept 14 days) so
      anyone reviewing a PR can download and try it
- [x] Test results: upload the `.xcresult` bundle as an artifact when a job fails
- [ ] Branch protection on `main`: require `test` and `build` to pass before merging
- [x] README: CI badge, and how to open a PR build (it's unsigned: right-click › Open, or
      `xattr -dr com.apple.quarantine Swanger.app`)

`release.yml`, on a pushed tag `v*`:

- [x] Run the same tests, then archive a Release build signed with the Developer ID Application
      certificate, imported into a temporary keychain from secrets (`DEVELOPER_ID_P12` base64,
      `DEVELOPER_ID_P12_PASSWORD`)
- [x] Notarise with `notarytool` using an App Store Connect API key (`ASC_KEY_ID`, `ASC_ISSUER_ID`,
      `ASC_KEY_P8`), then staple
- [x] Build `Swanger-<version>.zip` and `.dmg` with SHA-256 checksums; create a GitHub Release with
      generated notes and attach them (`permissions: contents: write` for this workflow only)
- [x] Update the cask in the Homebrew tap (`mrded/homebrew-tap`) with the new version and checksum, using a
      fine-grained token limited to that repo (`TAP_TOKEN`)
- [x] Document the secrets and how to cut a release in `CONTRIBUTING.md`

Until a Developer ID certificate is available, `release.yml` can publish the ad hoc build marked as a
pre-release; the signing and notarising steps are skipped when their secrets are missing.

### 3. Loading a spec (`SwangerCore`)

- [ ] `SpecLoader`: read a file URL; JSON vs YAML by extension, falling back to sniffing; YAML via Yams'
      `Node` API → `OrderedJSON`, keeping line/column for errors
- [ ] Version check from `openapi`: accept `3.0.x` and `3.1.x`; `swagger: 2.0` or anything else →
      `LoadError.unsupportedVersion(found:)`
- [ ] `LoadError` with file, line, column and message for parse errors
- [ ] Tests: JSON and YAML fixtures load to equal trees, key order preserved, bad YAML reports its line,
      Swagger 2.0 refused

### 4. `$ref` resolution

- [ ] `RefResolver`: JSON Pointer within a document (with `~0` / `~1` unescaping); relative file refs
      resolved against the referring file, each file loaded once and cached by URL
- [ ] Each resolved node remembers its origin (component name or `file#pointer`), used for fragment names
- [ ] Recursion: the second visit to a schema on the same path becomes a `recursive(origin)` node
- [ ] Broken refs never throw: they become `unresolved(ref, reason)` nodes and are collected as warnings
- [ ] Tests: local refs, cross-file refs, refs inside referenced files, a recursive tree schema, missing file,
      bad pointer

### 5. Normalising 3.0 to 2020-12

- [ ] `nullable: true` → `type: [T, "null"]` (and with `enum`, add `null`); boolean
      `exclusiveMinimum`/`exclusiveMaximum` → numeric; `example` → `examples: [example]`
- [ ] Runs once at load for 3.0 documents only
- [ ] Tests: each conversion, and a 3.0 and a 3.1 fixture describing the same schema produce equal models

### 6. The model

- [ ] Find roots: walk `paths.*.*.requestBody.content.*.schema` and `responses.*.content.*.schema`;
      prefer `application/json`, else the first JSON-like media type
- [ ] Root naming: the component name when the body is a `$ref`; otherwise `<operationId> request` /
      `<operationId> <status> response`, falling back to `<METHOD> <path>`. A component used by several
      operations is one root
- [ ] Root examples: the schema's `examples`, then the media type's `example` / `examples`
- [ ] `SchemaNode`: object (ordered fields), array (items), scalar, choice (`oneOf`/`anyOf` variants with
      discriminator: a property that is a `const` or single-value `enum` in every variant), recursive,
      unresolved. Field: name, required, type, constraints, allowed values, format/pattern, description,
      examples, fragment used, fragment defined in
- [ ] Keywords beside a `$ref` (allowed in 2020-12) tighten the fragment in place: fields forbidden with
      `not: {}`, newly required fields, extra constraints
- [ ] `Rule` wording in plain English: constraints ("must be one of …", "needs at least 1 item", "allows at
      most 70 characters"); `if`/`then`/`else` as "When `status` is "Rejected": `reason` is required";
      `oneOf`/`anyOf` as one case per variant ("When `type` is "Card": …") or, without a discriminator, as
      "exactly one of / at least one of" the variants' distinguishing fields; `dependentRequired`
- [ ] `FragmentIndex`: for each fragment, every root and path where it appears, direct or nested (`via`)
- [ ] Root stats: field, fragment and rule counts (as on the overview cards)
- [ ] `Spec` (the whole model) + `warnings: [LoadWarning]`
- [ ] Tests: hand-written fixture of a small API (orders/customers/addresses, with a discriminated `oneOf`,
      an `if`/`then`, a nested fragment, a recursive schema); snapshot tests of the rule text and the
      fragment index

### 7. Validation (`SwangerValidation`)

- [ ] Compile a root or fragment with swift-json-schema: wrap it in a document whose `$ref`s resolve to the
      (normalised) spec, so components and sibling files are found; cache compiled validators per schema
- [ ] Turn the library's basic output into `[ValidationIssue]` (type, pointer, message), as follows:
      keyword → type (*Missing*, *Wrong type*, *Not allowed value*, *Wrong format*, *Out of range*,
      *Unexpected field*, *Rule not met*); `required`/`additionalProperties` pointers include the field;
      condition branches use the schema's `description`; drop composition summaries explained below them;
      wrong type reported once; de-duplicate
- [ ] Skeleton payload for schemas with no examples: required fields only, first allowed value or a typed
      placeholder
- [ ] Example naming, so the menu says "type: Card" or "with reason" rather than "Example 2": differing
      fixed values, then which optional fields are present, then one level down, then the shortest
      differing value
- [ ] Test-case generator: from each example, a copy with each field in turn removed, set to `""`, `7`,
      `"zzz"`, `null`, `{}` and `[]`, and each object given an unexpected extra field
- [ ] Tests: every fixture example is valid as written; each broken case gives the expected type and pointer

### 8. App: document and window

- [ ] `DocumentGroup(viewing:)` with a read-only document: UTTypes JSON and YAML (`.yaml`, `.yml`);
      "Open With" registration in Info.plist
- [ ] `@Observable` `SpecStore` per window: loads on a background task, holds the `Spec`, warnings and
      selection
- [ ] `DispatchSource` file watching for the spec and every file it referenced; debounced reload keeping
      the selection; a failed reload keeps the old model with an error banner
- [ ] Error states: unreadable file (message, line, Reload), unsupported version, warnings badge listing
      unresolved refs
- [ ] `NavigationSplitView`: sidebar (search field, Overview, Request schemas, Response schemas, Shared
      fragments sorted by usage with the direct/nested dots), detail, and `.inspector`

### 9. App: overview, diagram, inspector

- [ ] Overview: a card per request schema with stats; the fragment usage grid (rows: fragments; columns:
      schemas; filled = direct, outlined = nested; hover shows paths; "Include responses" toggle)
- [ ] Diagram: cards are SwiftUI views; a custom `Layout` places them left to right; `Canvas` draws the
      connectors. Clicking a row that holds an object, array or choice opens its card; choice cards show
      one branch per variant with the discriminator; rules sit at the bottom of their card
- [ ] Pan by dragging, pinch and ⌘-scroll to zoom, zoom-to-fit; double-click opens a fragment's own page or
      shows a card on its own with "Show the whole schema"
- [ ] Colours: teal for top-level/required, amber for rules and decisions, violet for
      shared fragments; light and dark appearance
- [ ] Inspector: the selected field's details, its rules, "defined in" and "used in" links
- [ ] Search (⌘F): fields, roots and fragments, ranked by match quality. A field matches on its own name,
      never on the fields it sits inside; a dotted query (`address.postcode`) matches the end of a path; choosing a result opens and highlights it
- [ ] History: every move is a history entry; ⌘[ / ⌘] and swipe go back and forward, restoring the view

### 10. App: Try it

- [ ] `Diagram | Try it` segmented control in the toolbar
- [ ] JSON editor: `NSTextView` wrapper, monospaced, two-space indent on Tab, bracket matching
- [ ] Examples menu (named by task 7's rules) and skeleton fallback
- [ ] Debounced validation as you type; JSON syntax errors shown with their line
- [ ] Issue list under the editor; clicking an issue selects its range in the text (pointer → range map) and
      its row in the diagram, climbing to the nearest field the schema has; "Valid" state
- [ ] Edits kept per spec file and schema across launches

### 11. Hardening and release

- [ ] Real-world specs load without warnings or crashes and in reasonable time: Petstore 3.0 and 3.1, and a
      large public spec (e.g. GitHub's or Stripe's), as a test (downloaded in CI or kept as fixtures if the
      licence allows)
- [ ] UI smoke tests: open a fixture, select a schema, a valid payload shows "Valid", a broken one lists an
      issue
- [ ] App icon, About window, README screenshots
- [ ] A first signed, notarised release through `release.yml` (task 2) installs cleanly from the cask
- [ ] Tag `v0.1.0`

- `xcodebuild test` runs the UI smoke tests
- CI (task 2) runs both on every pull request and on `main`, and attaches a downloadable build to each run
